## 🔑 Key Components

### Ingestion Layer (`ingestion/`)

Copies files from local folders, preprocesses `ExSD-*.xlsx` files by removing unwanted sheets, extracts data, and writes CSV seeds. `seed_writer.py` also produces `*_metadata.txt` companion files recording row counts and distinct/null/duplicate key statistics — the first line of defence for catching source data quality issues before any transformation runs.

### Transformation Layer (`sqlmesh/`)

Cleans and models data using the Medallion architecture: Bronze (Raw) → Silver (Staging) → Gold (Marts). Parquet files are written via DuckLake with a DuckDB catalog.

**Data quality is enforced at every layer:**

| Layer | Mechanism | What it catches |
|---|---|---|
| Staging models | Inline `audits()` blocks | Duplicate surrogate keys, nulls, out-of-range measures |
| Fact models | Inline `audits()` + custom audit files | FK orphans, amount coherence |
| `audits/` directory | One standalone `.sql` file per custom audit | Complex cross-model integrity checks |

> **Bug fix (v0.4):** `stg_salesteam_data.sql` — `salesperson_id` was missing from the surrogate key hash, causing distinct salespersons sharing the same territory to receive an identical `salesperson_key`. Fixed by including `salesperson_id` as the first hash input. The inline `unique_values(salesperson_key)` audit now guards against any regression.

### Serving Layer (`serving/`)

`sync.py` copies Gold mart tables into `data/warehouse/serving.db`, a standalone DuckDB file that decouples BI tools from the transformation layer.

### Orchestration (`orchestration/`)

Dagster orchestrates the full pipeline as software-defined assets:
```
file_discovery → preprocessing → ingestion → transformation → serving
```
Runs on a 6 AM daily schedule with an optional file-sensor trigger.

### Reporting (`reporting/`)

Streamlit multi-page app connecting directly to `serving.db`.
